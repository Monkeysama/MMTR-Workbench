# 文档与议题写作约定

适用于项目文档、议题、PR 和进度回报。先写结果与实际限制，再写支撑证据；使用中文说明职责和约束，代码/API名称保持原名。

## 任务与进度

- 议题必须写清：当前问题、预期可观察结果、范围与非目标、依赖、可勾选验收、验证方法、下一检查点。优先级只设一个，`status:in-progress` 只用于当前主任务。
- 更新格式为“完成了什么；凭什么判断；尚未完成什么；下一检查点”。失败写明假设、实际现象和后续决定，不以测试数量表示效果进展。
- 不用百分比或小时承诺代替已完成节点。只有可复核的剩余任务才给时间估计，并说明前提。
- 历史路线在页首标明被哪个决策覆盖；当前索引只保留当前行动，避免堆叠互相冲突的“下一步”。

## 技术证据

- 每份研究报告注明日期、议题、输入/程序身份、执行范围、通过条件、实际结果、局限和下一步。
- 区分观察、推断与尚未证明；说明单帧/单材质/单版本边界。亮度均值接近不等于逐像素或完整受光等价。
- 静态、CPU、自有 GPU 宿主、捕获回放和游戏验证分别列出。失败与 skip 如实保留，不复制旧结果作为新版本验收。
- 线上文档使用仓库相对链接或真实 GitHub 链接。`output/`路径仅为本地复现索引，不当作读者可下载附件；原始资产和完整 IR 不上传。

## PR

开头说明具体问题和最终行为，列出关联议题、变更范围、验证命令/结果、已知缺口。范围改变时重写正文，不把历史对话追加成当前说明。没有完成全部议题验收时使用 `Refs #N`。
